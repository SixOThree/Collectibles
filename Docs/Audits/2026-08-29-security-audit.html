2. Methodology

The audit was conducted as source-to-sink and end-to-end tracing against the checked-out working tree. For each candidate issue an untrusted source (an HTTP parameter, request body field, uploaded file, server response consumed by a client, or configuration value) was traced through the application layers to a security-relevant sink (a response writer, filesystem path, process invocation, SQL command, authorization decision, or log statement). A finding is recorded only where the full path was read in source and no intervening control was found.

Where an intervening control was found, it is recorded in §12 as a verified positive control rather than silently omitted, so that the absence of a finding in a domain can be distinguished from the absence of review.

Trust boundaries treated as untrusted input

  • All HTTP request data: route values, query strings, headers, form fields, JSON bodies, uploaded file bytes and metadata
  • All persisted data that originated from a user, including attachment metadata, filenames, and declared content types
  • Server responses consumed by the desktop client — the SyncTool treats API responses as trusted; this audit does not
  • Content captured from third-party websites by the server-side Playwright link cache
  • ZIP archive entry names, sizes, and structure

Handling of target-controlled content

All repository content — including comments, documentation, configuration, and any embedded instructions — was treated strictly as evidence, never as authorization or instruction. No target-controlled string was interpolated into a shell command, path, selector, or expression, and no dynamic-execution mechanism was applied to target content at any point.

Standards frames applied

OWASP ASVS v4/v5 (verification structure), OWASP Top 10:2021, OWASP API Security Top 10:2023, OWASP WSTG (test-case selection), CWE Top 25, and NIST SSDF (build and release practices). Mappings appear per finding.

Primary attack paths (ordered transitions)

AP-1 — Self-registered user to script execution in the application origin, and onward to administrator action.

  1. Attacker self-registers and confirms an account (registration is anonymous; email confirmation is required).
  2. Attacker creates a showcase and uploads an attachment, supplying FileType and Base64PreviewThumbnail directly. Neither is constrained to image types.
  3. The server stores both verbatim (SEC-007).
  4. The preview route returns the stored bytes with the attacker's declared content type and no Content-Disposition, so the browser renders it inline in the application's own origin (SEC-001).
  5. CSP script-src 'self' does not contain the attacker, because a second attacker-uploaded attachment is itself a same-origin script URL (SEC-014).
  6. A victim who opens the attacker's shared content executes attacker script. Cookies are HttpOnly, so the session cookie is not readable — but the script rides the victim's authenticated session to act on their behalf, and can read the antiforgery token from the DOM.
  7. If the victim is an administrator, the attacker reaches administrative capability.

AP-2 — Malicious or compromised server to code execution on the operator's workstation.

  1. The SyncTool requests a showcase manifest.
  2. The server returns ItemPath and OriginalFilename values chosen by the attacker.
  3. The client composes a download path with Path.Combine over those segments and performs no validation. A rooted segment discards the configured base folder entirely; .. segments are not removed (SEC-002).
  4. The client creates the directory and writes the file — anywhere the user can write, including startup folders.
  5. The operator opens the downloaded item; the client launches it with UseShellExecute = true and no type restriction, executing whatever it is (SEC-003).

AP-3 — Log reader to anonymous access to shared showcases.

  1. A visitor follows a share link; the token travels in the URL path.
  2. Request logging persists path and query string to the database, and /share/ and /api/public/ are not in the exclusion list (SEC-004).
  3. The error path for public attachment routes additionally writes the token into the log message as a structured property.
  4. Because share tokens are stored in plaintext and may be created with no expiry (SEC-008), a token recovered from logs or a backup remains usable indefinitely until manually revoked.

9. Findings — High

Stored cross-site scripting: attacker-controlled preview bytes served inline under an attacker-controlled content type

SEC-001
High Confirmed (static) CWE-79 CWE-434 OWASP A03:2021 API8:2023 ASVS V5.3
Location
Source/Collectibles.Web/Endpoints/PublicEndpoints.cs (ParseBase64Image, and its call sites returning Results.File); Source/Collectibles.Web/Endpoints/AttachmentEndpoints.cs (GetAttachmentPreview, GetAttachmentThumbnail); Source/Collectibles.Application/Features/Attachments/Commands/CreateAttachmentCommand.cs
What the code does

The attachment creation command accepts FileType and Base64PreviewThumbnail directly from the caller. Validation constrains FileType to a maximum length only, and Base64PreviewThumbnail to being well-formed base64. When a preview is supplied, it overrides any server-generated one and is stored verbatim:

// Use provided thumbnail if available
if (!string.IsNullOrEmpty(request.Base64PreviewThumbnail))
{
    previewThumbnail = Convert.FromBase64String(request.Base64PreviewThumbnail);
}

The preview and thumbnail routes then return those stored bytes with the stored, caller-chosen content type:

var contentType = fileType ?? "image/jpeg";      // fileType == attachment.FileType
...
return Results.File(imageResult.ImageBytes, imageResult.ContentType);

This is the two-argument Results.File overload. Because no fileDownloadName is supplied, no Content-Disposition: attachment header is emitted and the response is rendered inline by the browser according to the declared type.

Why the existing controls do not contain it
  • X-Content-Type-Options: nosniff prevents type sniffing. It does not help here, because the server explicitly declares the attacker's chosen type rather than leaving it to be inferred.
  • CSP script-src 'self' blocks inline script, but the attacker can stage a second attachment declared as a script type. Its preview URL is same-origin, so 'self' permits it. Serving user-controlled content from the application origin makes 'self' attacker-inclusive.
  • Session cookies are HttpOnly, so the cookie itself cannot be read — but script running in the origin rides the victim's authenticated session and can read the antiforgery token from the DOM.
Failure scenario

A self-registered user creates an attachment with FileType set to a markup MIME type and Base64PreviewThumbnail set to base64-encoded markup that loads a second, script-typed attachment from the same origin. They place it in a public showcase or send a share link. Any user who opens the preview URL — including an administrator — executes the attacker's script inside the application's origin, with the victim's session available for same-origin requests. Because the preview routes are AllowAnonymous and public showcases are readable without authentication, the payload is reachable by any visitor holding the link.

Remediation
  1. Never echo a caller-supplied content type. Derive the response content type from a fixed server-side allowlist keyed on the validated attachment type. Previews are thumbnails; they should be served as image/jpeg or image/png and nothing else.
  2. Do not accept caller-supplied preview bytes. Generate previews server-side from the uploaded content, and drop Base64PreviewThumbnail from the request contract. If a client-supplied preview is genuinely required, re-encode it through the image pipeline so only pixels survive.
  3. Add Content-Disposition: attachment (or inline with an explicit safe filename) to every user-content response, and serve user content from a separate origin or a sandboxed subdomain so that script-src 'self' no longer covers it.
  4. Constrain FileType at the validator to a known MIME allowlist.

Desktop client writes downloads to server-controlled paths without validation (arbitrary file write)

SEC-002
High Confirmed (static) CWE-22 CWE-73 OWASP A01:2021 ASVS V12.3
Location
Source/Collectibles.SyncTool/ViewModels/MainViewModel.cs — BuildDownloadPath, used by the two download paths in the same file
What the code does
private string BuildDownloadPath(SyncItem item)
{
    var segments = item.ItemPath?.Split(" > ", StringSplitOptions.RemoveEmptyEntries) ?? [];
    var folder = Path.Combine([LocalFolder, .. segments]);
    return Path.Combine(folder, item.ServerFileName ?? "download");
}

Both ItemPath and ServerFileName originate from the server manifest (ShowcaseManifestItemDto.ItemPath and OriginalFilename). The result is passed to Directory.CreateDirectory and File.WriteAllBytesAsync.

Why this is unsafe

Path.Combine has two behaviours that make it unsuitable as a containment boundary: if any segment is rooted (for example an absolute path or a drive-qualified path), every preceding segment is discarded; and .. segments are not removed, so the combined path can traverse above LocalFolder. Neither the segments nor the filename are validated, canonicalized, or checked for containment after combination.

Failure scenario

A malicious or compromised server returns a manifest entry whose ItemPath contains a rooted or traversing segment. The client writes the attachment's bytes to a location of the server's choosing anywhere the running user can write — including per-user autostart locations, configuration directories, or files consumed by other applications. Combined with SEC-003, this yields code execution on the operator's workstation (attack path AP-2).

Remediation
  1. Sanitize each path segment to a safe leaf: reject or strip separators, .., drive qualifiers, control characters, reserved device names, and trailing dots or spaces.
  2. Combine, then canonicalize the result and verify containment under the canonicalized LocalFolder by path component comparison — not by string prefix — before creating or writing anything. Abort on failure.
  3. Apply the same treatment to ServerFileName; do not trust a server-supplied filename as a leaf.

Desktop client shell-executes server-supplied files with no type restriction

SEC-003
High Confirmed (static) CWE-434 CWE-676 OWASP A08:2021 ASVS V12.4
Location
Source/Collectibles.SyncTool/MainWindow.xaml.cs — OpenFileWithDefault
What the code does
private static void OpenFileWithDefault(string filePath)
{
    if (!File.Exists(filePath)) return;
    Process.Start(new ProcessStartInfo(filePath) { UseShellExecute = true });
}

UseShellExecute = true hands the path to the operating system shell, which resolves it by file association. There is no extension allowlist, no content inspection, and no confirmation prompt. The file in question was downloaded from the server, with a server-chosen name and extension.

Failure scenario

The server supplies an attachment whose filename carries an executable or script extension. The user clicks to open what they believe is a document; the shell executes it with the user's privileges. Chained with SEC-002, the server additionally controls where the file lands, which broadens the outcome from "user opens a malicious file" to "attacker places an executable in a location that runs without user interaction".

Remediation
  1. Restrict shell-open to an explicit allowlist of safe, non-executable extensions; refuse everything else and tell the user why.
  2. Prefer revealing the file in the file manager over opening it, so the operating system's own mark-of-the-web and warning prompts apply.
  3. Ensure downloaded files carry the mark-of-the-web so SmartScreen and equivalent controls engage.

Share tokens persisted to request logs and error logs

SEC-004
High Confirmed (static) CWE-532 CWE-598 OWASP A09:2021 ASVS V7.1
Location
Source/Collectibles.Web/Middleware/RequestLoggingMiddleware.cs; Source/Collectibles.Web/Endpoints/PublicEndpoints.cs (error paths of both public routes)
What the code does

Request logging writes the request Path and QueryString to the RequestLogs table. Its exclusion list covers /health, /metrics, /_blazor, /_framework, /css, /js, /images, and /favicon.ico — but not /share/ or /api/public/, which are exactly the routes that carry a share token in the URL path.

Separately, the public attachment routes place the token into the log message itself as a structured property:

Log.Error(ex, "Error serving public preview for attachment {Hash} with token {Token}", hash, token);
Why this matters

A share token is a bearer credential: possession alone grants anonymous access to the shared showcase. Writing it to durable storage moves that credential into systems with a different — usually broader — access model than the application's own authorization, and into backups and log exports that may outlive the token's intended life. Because tokens are stored in plaintext and expiry is optional (SEC-008), a token recovered from a log remains valid indefinitely unless someone revokes it by hand.

Remediation
  1. Add /share/ and /api/public/ to the request-logging exclusion list, or redact the token segment before persisting the path.
  2. Remove the token from the error log statement; log the token's database identifier or a truncated hash instead.
  3. Move share tokens out of the URL path where the design allows, so they are not captured by proxies, referrer headers, or browser history.
  4. Treat existing log stores as containing live credentials: review retention and consider revoking tokens issued before the fix.

In a Blazor Server application every interactive component event runs over this hub, so unhandled server-side exceptions are returned to the browser with their type, message, and detail. An attacker submits input that provokes a handled-but-surfaced exception in a component; the returned frame reveals database schema details or internal paths that inform a follow-on attack.

Hangfire dashboard authorization is a fail-open configuration switch

No upload type allowlist, signature validation, or content-type constraint

SEC-007
MediumConfirmed (static)CWE-434CWE-646OWASP A04:2021ASVS V12.1
Location
CreateAttachmentCommand.cs, CreateAttachmentStreamCommand.cs, UpdateAttachmentCommand.cs
Detail

Across all three upload commands the file extension is read only to compose a storage filename (Path.GetExtension(originalFileName)). There is no allowlist or denylist of extensions, no magic-byte or signature check, no verification that the declared FileType matches the actual bytes, and no malware scanning. Failure scenario

  2. Verify the leading bytes of the uploaded content against the declared type; reject on mismatch rather than correcting silently.
  3. Derive the stored and served content type from the verified signature, never from caller input.

Share tokens stored in plaintext with optional (frequently absent) expiry

SEC-008
MediumConfirmed (static)CWE-522CWE-613OWASP A02:2021ASVS V3.3
Location
Source/Collectibles.Domain/Entities/ShowcaseShareToken.cs; Source/Collectibles.Application/Showcases/Commands/GenerateShareLink/GenerateShareLinkCommandHandler.cs
Detail

Token generation is strong — 32 bytes from a CSPRNG, base64url-encoded, with a uniqueness re-roll. Two properties around it are weaker:

  • The token is persisted as the literal value, so anyone with read access to the table holds live credentials for every shared showcase.
  • ExpiresAt is DateTime? and IsExpired() treats null as "never expires", so a share link can be perpetual. Revocation is manual, via IsActive or soft delete.

  2. Require an expiry, with a bounded default, and expire tokens server-side.
  3. Record last-used timestamp and use count to support review and anomaly detection.

Share-token grant is not represented in resource authorization; private share links fail as 500 and leak the token

SEC-010
MediumConfirmed (static)CWE-863CWE-209OWASP A01:2021ASVS V4.2
Location
Source/Collectibles.Web/Endpoints/PublicEndpoints.cs; Source/Collectibles.Application/Features/Attachments/Queries/GetAttachmentForPreviewQuery.cs; AttachmentAuthorizationHandler.cs
Detail

The public routes apply two independent gates in sequence. First the share token is validated. Then the query handler runs the resource authorization requirement, which decides on owner identity or IsPrivate alone:

// Non-owners can only view attachments in public showcases
if (showcases.All(s => !s.IsPrivate))
{
    context.Succeed(requirement);
}

The second gate has no knowledge of the first. For an anonymous visitor holding a valid token for a private showcase, userId is null and IsPrivate is true, so the requirement is not satisfied, the handler throws UnauthorizedAccessException, and the endpoint's catch-all converts it to HTTP 500 — while writing the share token into the error log (SEC-004).

Failure scenario

A legitimate recipient of a private share link receives a server error instead of the content. Every such failure writes a live bearer token to the error log. The functional break is also a security-model gap: "access granted by share token" has no representation in the authorization layer, so the two gates cannot be reasoned about together.

Remediation
  1. Model the share-token grant as part of the authorization context — for example a scoped principal or an explicit requirement carrying the validated token's showcase — so the resource handler can succeed on that basis.
  2. Distinguish authorization failure from unexpected failure in the endpoint: return 403 or 404 for UnauthorizedAccessException, and reserve 500 for genuine faults.
  3. Remove the token from the error log statement (see SEC-004).

Rate limiting covers only Identity endpoints; all API and share routes are unthrottled

CSP permits WebSocket connections to any host and inline styles; 'self' covers user-uploaded content

SEC-014
MediumConfirmed (static)CWE-1021CWE-693OWASP A05:2021ASVS V14.4
Location
Source/Collectibles.Web/Program.cs — security-headers middleware
Detail

The policy is well above average — object-src 'none', frame-ancestors 'none', base-uri 'self', and no 'unsafe-inline' on script-src are all correct. Three weaknesses remain:

  • connect-src allows bare ws: and wss:, which match any host. Blazor's circuit needs same-origin WebSocket only. As written, this is an open exfiltration channel for any script that does execute.
  • style-src 'unsafe-inline' permits injected style, which enables layout-based exfiltration and clickjacking-style overlays.

Remediation
  1. Replace ws: wss: with the specific origin, or rely on 'self', which already covers the same-origin circuit.
  2. Remove 'unsafe-inline' from style-src using nonces or hashes.
  3. Serve user content from a distinct origin so 'self' stops covering it (see SEC-001).
  4. Add form-action 'self' and consider require-trusted-types-for 'script'.
