1 · Executive Summary

This audit inspected the full Collectibles solution — a .NET 10 (SDK 10.0.101), C# 14, Blazor Server application built on Clean Architecture and CQRS (MediatR 14.1), EF Core 10 / SQL Server, Hangfire, FluentValidation, Serilog, ASP.NET Core Identity, a pluggable storage/email layer, Playwright-based external-link capture, and a companion WPF sync tool. Eight subsystem passes plus repository-wide cross-cutting passes were run; baseline diagnostics (restore, build, test, format, package vulnerability/deprecation, npm audit, coverage) were captured. The build is green (0 errors) and all 242 unit tests pass, but the audit surfaced material correctness, data-integrity, authorization, and security issues beneath that green status.

Headline risks. The most severe issues are not visible to the compiler or the current test suite: an administrator migration-rollback path that can destroy the only surviving copy of an attachment; the absence of any global soft-delete query filter, so "deleted" content resurfaces across list, download, and public-share paths and — via drifted orphan-cleanup logic — can be permanently purged from storage; a server-side request-forgery (SSRF) surface in the Playwright link-capturer that fetches arbitrary user-supplied URLs from a privileged network position; a path-traversal write primitive in the default local file-storage provider; systemic inconsistency in per-handler authorization (several mutating commands enforce nothing while their siblings do); and a client-overridable UserId on multiple commands/queries that moves identity into the request contract. None of the four working-tree secrets were ever committed (verified across all git refs), but they sit in cleartext locally and should be rotated and relocated.

Overall posture: The architecture is coherent and the happy paths are well built, but safety-critical invariants (soft-delete visibility, single-durable-copy, per-resource authorization, egress validation, filesystem containment) are enforced by convention rather than centrally, and have drifted. Prioritized remediation should begin with the Critical/High correctness, data-integrity, security, and authorization items before quality and hygiene work.

2 · Scope, Assumptions & Limitations

The audit universe was the tracked files plus non-ignored untracked files under the repository root (1,028 tracked files excluding the four in-tree .worktrees/ checkouts, which were excluded throughout). Content-level review covered all custom C#, Razor, TypeScript/JavaScript, configuration, project, solution, and documentation files. Generated migrations, vendored/minified wwwroot assets, bin/, obj/, node_modules/, and tool caches were inventoried and provenance-assessed but not line-audited.

  • Method & authority. Findings prioritize observable behavior and traced runtime paths, then domain/security invariants, then repository configuration and tests, then current Microsoft/library documentation, then general principles. Suspected defects were traced through callers, persistence, and authorization before being classified Confirmed. Severity reflects consequence magnitude and blast radius only; confidence reflects evidence strength; exposure/likelihood is described in each finding's triggering-conditions.
  • Version-sensitivity. A few EF Core 10 / Blazor .NET 10 behavioral claims (execution-strategy + user-transaction interaction, filtered-include semantics, prerender double-execution) are stated from ≤EF Core 9 / prior Blazor behavior and are marked Medium confidence with the exact verification named; no behavioral change was found announced, but they were not runtime-confirmed here.
  • Safety skips. Running the application, executing the Node Playwright E2E suite, and EF design-time commands (dotnet ef, which executes app-startup code) were not performed: they require a live, isolated SQL Server / storage / browser environment that could not be guaranteed disposable. These are recorded as limitations, not as verified-correct. The xUnit suite was run because its fixtures use per-test GUID-named EF InMemory databases and per-instance temp directories (verified isolated).
  • Coverage limits that affect confidence. Infrastructure (1.3%) and Web (1.4%) have almost no automated coverage, so several Probable-risk findings in those layers could not be runtime-confirmed. The two prerender/execution-strategy items depend on unrun runtime behavior. Secret values encountered were redacted (presence reported only).
  • Write boundary. The only repository output intentionally created is this canonical report at Docs/Audits/2026-08-29-application-audit.html. No source, config, dependency, migration, test, or documentation file was modified. Diagnostic artifacts were written only to the OS temp scratchpad. The working tree was verified clean before and after every repository-controlled diagnostic.

4 · Actual Architecture & Documentation Drift

Actual solution. Five source projects — Collectibles.Domain (79 C# files, framework-pure POCO entities/value-objects/constants), Collectibles.Application (218 files; ~95 MediatR requests, ~93 handlers, 22 FluentValidation validators, 9 resource-based authorization handlers), Collectibles.Infrastructure (86 files + 37 EF migrations; persistence, ~30 services, storage/email providers, media, Playwright capture), Collectibles.Web (37 C# + 135 Razor + 13 custom JS; Blazor Server host, minimal-API endpoints, middleware, Identity), and Collectibles.SyncTool (WPF net10.0-windows). Dependency direction is broadly correct (Domain ← Application ← Infrastructure/Web), with noted framework leakage into Application (EF Core in ~70 files; static Hangfire.BackgroundJob.Enqueue in 3 handlers).

Key reconciliations (documented vs. actual):

  • Phantom Kernel project. README, DEVELOPER_README, and CONTRIBUTING document a Collectibles.Kernel "5th layer" for constants/HashIds. It does not exist as a project (only an empty, untracked husk directory remains); ApplicationConstants lives in Domain.   • Solution references missing files. Collectibles.sln lists azure-pipelines.yml and CLAUDE.md as solution items; neither exists. No CI definition exists anywhere, yet Collectibles.Web.csproj advertises "Updated by Azure Pipeline during CI/CD" (F-046, F-048).
  • SyncTool omitted. The README architecture diagram omits the real Collectibles.SyncTool project while documenting the non-existent Kernel.

Substantive claims in the older SECURITY_REVIEW.md / ARCHITECTURE_REVIEW.md were spot-checked and remain accurate, but all their deep links point at a foreign machine's checkout path and are dead in this repository.

F-001Migration rollback can destroy the only remaining copy of an attachment's contentCriticalConfirmed defectConf: High
Category / Subsystem
Data integrity · Application → Infrastructure storage (Attachments migration ops)
Evidence
Source/Collectibles.Application/Features/Attachments/Commands/RollbackAttachmentMigrationCommandHandler.cs:107-143 — deletes blob (line 111) + preview (117) BEFORE nulling FilePath/PreviewPath/IsMigrated (137-140), with no check that AttachmentContent still holds the DB copy. CleanupMigratedAttachmentsCommandHandler — nulls the DB AttachmentContent for migrated attachments.
Affected behavior & path
An admin runs "migrate to Azure" → later "cleanup migrated" (DB content nulled to reclaim space) → later "rollback" with DeleteFromStorage=true: the handler deletes the blob and sets FilePath=null, leaving the attachment with content in neither the database nor storage. The handler's own comment (lines 99-101, 145) acknowledges no transaction protects the delete+update pair.
Root cause
Rollback assumes the DB copy is intact; no precondition check; three admin maintenance operations are individually safe but not composition-safe, and irreversible storage deletion precedes (and is not gated by) confirmation that another durable copy exists.
Impact & triggering conditions
Permanent, unrecoverable content loss across an admin-selected batch. Requires the migrate → cleanup → rollback(DeleteFromStorage) sequence; exposure is admin-only, but consequence is total data loss with no recovery path.
Violated invariant
"At least one durable copy of attachment content must exist at all times." Irreversible side effects must follow a committed transactional write, not precede it.
Recommended correction
Before deleting storage, verify AttachmentContent.Content != null (or the DB copy is otherwise restorable); skip-and-report any attachment lacking a DB copy; delete the blob only after the DB restore is committed. Consider an Infrastructure-level transaction wrapper so rollback is atomic.
Verification method
Unit/integration test: rollback an attachment whose AttachmentContent was nulled by cleanup; assert the handler reports an error and leaves the blob untouched.
Related
F-012 (delete-then-save), F-018 (delete-semantics inconsistency). Occurrences: 1 handler; compositional with CleanupMigratedAttachments.

Category / Subsystem
Soft delete / query correctness · DbContext + ~37 Application query files
Evidence
HasQueryFilter: 0 matches solution-wide (verified). `Deleted == null` written by hand 89 times across 37 files. Confirmed omissions on soft-delete entities: GetAttachmentsListQuery.cs:56-58; GetAttachmentByIdQuery / GetAttachmentForDownloadQuery / GetAttachmentForPreviewQuery.cs:50-56 (0 Deleted predicates) Tags/Queries/GetTagsListQuery.cs:24-27 (SearchTagsQuery filters; this one does not) ShowcaseShareTokenRepository.cs:22-35 (includes s.Showcase without filtering the showcase's own Deleted)
Affected behavior & path
DeleteCollectibleItemCommand soft-deletes attachments, then GetAttachmentsListQuery / GetAttachmentForDownloadQuery return them; a soft-deleted showcase continues to serve its items, tags, and preview blobs through an active share link. Item/child counts disagree between paths that filter and paths that don't.
Root cause
Soft delete is a per-query convention, not enforced centrally via HasQueryFilter(e => e.Deleted == null) on ISoftDelete types.
Impact & triggering conditions

Violated invariant
A global invariant ("deleted rows are invisible") must be enforced once, centrally — not restated 89 times where any omission silently breaks it.
Recommended correction
Add model-level query filters for all ISoftDelete entities in OnModelCreating; audit the admin/restore paths that then need IgnoreQueryFilters. Consider a SaveChanges interceptor converting Remove on ISoftDelete into a soft delete.
Verification method
Integration test: soft-delete an attachment; assert its absence from every attachment query and the share-link path. The count of manual Deleted == null predicates should fall toward zero.

F-005Server-side request forgery: Playwright navigates to arbitrary user-supplied URLsHighConfirmed defectConf: High
Category / Subsystem
Security (SSRF) · Infrastructure link-capture background service
Evidence
ScopedLinkProcessorService.cs:65 await page.GotoAsync(cache.LinkInfo.Url); // no scheme/host validation, redirects followed Input: AddLinkToCollectibleItemCommandHandler stores request.Url verbatim (no FluentValidation validator exists for the command). Served back: LinkCacheEndpoints.cs:69-75,119-125 (owner-only). Gated by ExternalLinks:Enabled=true (default ON).
Affected behavior & path
Any authenticated user adds a "link" (e.g. http://169.254.169.254/…, http://localhost:port/…, an internal hostname, or file:///…). The background Chromium fetches it server-side; the rendered HTML and full-page screenshot are stored and returned to the user — a read-back SSRF against internal networks and cloud metadata endpoints, with redirects followed. The page object is also never closed (leak) and the row is stuck in Processing if the process crashes (only Pending is re-queried).
Root cause
No egress validation of the target URL (scheme allowlist, public-IP resolution, redirect re-check) before navigation.
Impact & triggering conditions
Internal-network/metadata exfiltration from a privileged position; triggered by adding a link with external-links enabled (the default). Consequence scales with the host's network reachability (cloud metadata, internal admin panels).
Violated invariant
Never fetch attacker-controlled URLs from a privileged network position without egress validation.
Recommended correction
Validate scheme (http/https only); resolve DNS and reject loopback/link-local/private ranges; re-validate after each redirect (request interception); apply explicit navigation/screenshot timeouts; close the page per link.
Verification method
In an isolated env, add a link to http://169.254.169.254/ and observe the capture attempt; confirm rejection after the fix.

Category / Subsystem

Evidence
Pattern `request.UserId ?? _currentUserService.UserId` used as the authorization/audit identity in: CreateCollectibleItemCommand, CreateShowcaseCommand, GenerateQRCodesCommand, CreateZipUploadJobCommand/StreamCommand:49, InitializeChunkedUploadCommand, CompleteZipDirectUploadCommand, SyncUploadCommand, GetShowcasesListQuery:32.
